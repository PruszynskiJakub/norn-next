# Friction and defects — sync-qa targeted rerun (impl-base-sync-qa @ afa89c0)

Ranked by impact on a person. Evidence paths relative to this directory.

## D1 — `stale:<story>:<sha>` Check item flaps whenever a behind-and-conflicting story parks on an implicit ask, in any step (MED, noise + wrong advice)
BS10's `stale:*` item is meant for a story waiting at a gate *without* a `stale` route. On B it appeared **17 times** for gh-44 (inbox-history-pr-items.txt, inbox-history-B.json): every time the unit parked on a permission prompt — in implement (17:24, right after S1 merged), review, qa and resolve — and was resolved again by my answer or the agent's `done` a few seconds later. Each one says "gh-44 conflicts with main in … — `norn update gh-44`", which is wrong advice: the workflow is already headed to (or inside) `update`/`resolve`; at 17:29:17Z it fired while resolve#1 was merging exactly that base (b-trace-gh44-resolve-decisions.txt). The rule seems to treat any `parked` unit as "waiting at a gate". Should fire only for `park.kind == gate` on a gate step without a `stale` route.

## D2 — the agent's merge commit carries norn's deferred runs/ files (LOW)
While the merge was in progress norn deferred its own commit (correct, H1). The resolve agent then concluded the merge with `git add -A; git commit --no-edit` (its own command), so the merge commit c4d2868 contains norn's `state.json`, `0018-ask.json` and `0019-answer.json` next to the resolution (b-after-merge-commit.txt). ## D3 — While a merge is in progress, `recover.commit` starves every other rule of the unit: a second prompt mid-merge is invisible, deadline/stalled never fire (HIGH)
gh-44 resolve#2 on B (herdr): the agent hit a prompt mid-merge (17:41:48Z), norn parked it (commit deferred — correct), I answered (`receipts.apply` 17:42:33Z, unit back to `running`). The working tree still has MERGE_HEAD + unmerged paths, so the unit's runs/ files stay `uncommitted`, and `decide.ts:480` (`if (uf.uncommitted) … recover.commit`) returns before the status switch on every tick. The agent's next command — the `git add … && git commit` that would conclude the merge — hit a second prompt; the pane fact was `waiting_input` on every tick from 17:42:33Z, yet the only decision was `recover.commit` → `deferred` (b-trace-gh44-resolve2.txt). Result: `norn status` "running resolve#2 16m … ask since 17:41:48" (stale ask time), `norn inbox` lists it under Running, **no Answer item for 16 minutes**; `norn answer gh-44 1` refused `not_parked_on_ask` (b-answer-hidden-prompt.json); the 15 m step deadline passed (17:56:29Z) with no `timeout` either. By reading the same branch: `died`, `silent`, `stalled` and `timeout` are all unreachable for a unit whose worktree is mid-merge, so an agent that dies mid-merge would hang the story silently. H1's "defer" is right; the defect is that the deferral is decided *instead of* the unit's other rules. Fix direction: when the owed commit is deferred by a git operation in progress, fall through to the status switch (or treat it as a non-blocking side note), and have the implicit-ask rule re-raise when the pane is `waiting_input` after an answered ask. Workaround used: pressed Enter in the herdr pane myself (`herdr pane send-keys w22:p1 Enter`); the agent concluded the merge (dd3f69d, 2 parents, no markers) and `norn done` was accepted.

## D4 — A person's push to a `$done` story branch always ends in `stuck: diverged` on `norn update`; BS3.3's fast-forward cannot happen from `$done` (MED)
After I pushed one commit (ec39a62, README) to origin/gh-45 while the story was `$done`, norn kept committing locally on top of the old head — d0edf1e "norn: gh-45 $done (recovered commit)", then `norn update`'s receipt commit 5321778 — without fetching/fast-forwarding first. update#7 then found the branches diverged and went `$stuck` "story branch diverged from origin/gh-45-…", and the push of the stuck commit was rejected (non-fast-forward, second Unblock item). The head-changed item told me about the commit correctly, but the only way forward was a person `git merge` in the worktree + `norn unstick` (snaps/16-gh45-diverged). BS3.3 assumes the remote is a descendant of local ("a person pressed Update branch"); that only holds if norn makes no local commit in between. Fix direction: before writing a receipt commit on a story whose remote moved (e.g. `norn update` from `$done`, recovered commits), fast-forward when local has only norn's runs/ commits on top, or merge the remote head the way `update` merges the base (trailer-tagged), since a person's commit on the story branch is legitimate input.

## D5 — norn pushes an agent's merge commit that still has conflict markers (HIGH; H1 closes only norn's own commits)
gh-44 resolve#3 (B): the agent's one-shot command `sed -i -e … handoff.md` (GNU syntax, fails on macOS) followed by `git add -A && git commit` concluded the merge as 9863241 with `<<<<<<< HEAD / ======= / >>>>>>> 16106cd` still in the repo-root `handoff.md` (b-9863241-handoff-markers.txt). When the agent then hit a prompt, norn's park commit 960e0aa ("resolve waits for input": only runs/ files, so the `git_conflict_markers` guard passed) **pushed the branch, publishing 9863241 with markers** to origin/gh-44 (markers-scan-1.txt: both commits' trees contain markers in handoff.md). H1's guard looks at norn's staged diff only; the push carries every unpushed agent commit. BS5's `norn done` check ("no markers remain") would still stop the step, so nothing reaches main unless the agent fixes it — but the published story branch (and the draft PR head) carries markers in between. Also note: the check suggested for this rerun, `git log -p origin/<branch> | grep '^+<<<<<<<'`, prints nothing for merge commits (git log -p shows no diff for merges without `-m`/`--cc`); scan trees instead (`git grep -e '^<<<<<<< ' <commit>` per `git rev-list`). Fix direction: before any push, scan the commits being pushed (`git rev-list origin/<b>..HEAD`) for added marker lines (`git diff --check`-like, including merge commits vs first parent) and hold the push (trace + Unblock) instead of publishing.
