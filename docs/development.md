# Development

The contributor reference for norn's own code: the commands, the test tiers and CI, the plugin contract and the suites that hold every plugin to it, where each contract lives, how a release runs, and the design decisions behind the code. The short map an agent reads first is [`AGENTS.md`](../AGENTS.md); the person's side of contributing is [`CONTRIBUTING.md`](../CONTRIBUTING.md).

## Commands

```sh
bun install
bun run test        # the unit tier, in seconds: your loop after each change; a plain `bun test` runs exactly this
bun run test:integration  # the integration tier (packages/*/test/integration/), 6 workers: CI runs it in shards, never a local check
bun run typecheck   # tsc --noEmit over every package and scripts/
bun run schema:emit # regenerate packages/schema/json/*.schema.json after changing a schema
bun run docs:emit   # regenerate the generated blocks of docs/reference.md, docs/workflows.md and CONTRIBUTING.md after changing a command, flag, config key, or a workflow or skill of the pack or .agents/workflows/
bun run build       # dist/npm/: one bundled norn.js + package.json; build:bin [<target>…] builds the binaries
bun run golden -- --update  # behaviour change: re-decide every golden case, rewrite only its decisions
bun run golden      # add the golden cases the scenarios in packages/kernel/scripts/golden/ produce
```

To run the integration tests of one package, as you do after changing it: `bun test --config=bunfig.integration.toml --timeout=60000 packages/<pkg>`. The cli's integration tests cannot run inside a norn agent step: their person-only `norn` calls run below the agent's process, which the CLI refuses (`person_only`), so `world()` (`packages/cli/test/integration/world.ts`) fails every test at once with that reason. Run them from a shell of your own, or leave them to CI.

## Layout

norn is a thin kernel with a plugin contract. The kernel decides; plugins fill **slots** and do one effect per call; the runtime hosts both; the cli wires the plugins a config picks and offers the commands.

```
packages/schema           @norn/schema           JSON Schemas (TypeBox) + types + ajv validators, ids, the CliError and ExitCode contract
packages/plugin-api       @norn/plugin-api       the plugin contract: defineNornPlugin, the slots, HostContext, PluginResult, harness events, story keys, the plugin API version
packages/kernel           @norn/kernel           pure: workflow loader and counters, the model (facts, actions, receipts, run state), decide, the journal's write rules, the session reducer and classifier, the brief
packages/runtime          @norn/runtime          the host: tick (lock, gather facts, decide, act, trace), slot resolution, the launcher (executor = harness + runner), hook ingest and event log, inputs and skills in worktrees, detached checks, the open-pr, await-checks and await-merge step kinds
packages/host-node        @norn/host-node        the HostContext over Bun and node: atomic file writes, exec with a bound, detached processes; beside it, `serveHttp`, the loopback HTTP server the lab dashboard is served by
packages/vcs-git          @norn/vcs-git          the vcs slot over git (worktrees, merge, push, refs) and the update-branch, integrate, push and verify-base step kinds
packages/tracker-local    @norn/tracker-local    a tracker over one markdown file per item
packages/plugin-github    @norn/plugin-github    a tracker over issues and a forge over pull requests, through gh
packages/forge-none       @norn/forge-none       a forge for a repo with no code host: a local record of each change, merged with git
packages/store-local      @norn/store-local      a store in the machine dir (runs-v2/stories/<story>/…)
packages/store-refs       @norn/store-refs       a store on git refs (refs/norn/v2/…) shared through the remote
packages/harness-claude   @norn/harness-claude   the Claude Code harness: hooks in .claude/settings.local.json, launch, normalize, respond
packages/harness-pi       @norn/harness-pi       the pi harness: an extension pi loads, launch, normalize, respond
packages/harness-lab      @norn/harness-lab      the lab harness: a scripted stand-in agent (`runLabAgent`, run as `norn lab-agent`) playing a beat script, launch, normalize, respond; it honours a denied tool call (`denyTool`), so docs-only steps run on it, and a resumed session or a retry (`retry` in `norn brief --json`) plays its beat's `resumed` work
packages/runner-headless  @norn/runner-headless  agents as detached processes, output to a log
packages/runner-herdr     @norn/runner-herdr     agents in Herdr panes, one workspace per story and one tab per run, closed by `close` (plugin API 1.17) once the run's unit is done with; `focus`, `split` and `label` (plugin API 1.18) bring a run's pane in front, open the cockpit below a person's pane and write a story workspace's `$norn` sidebar token
packages/pack-sdlc        @norn/pack-sdlc        the sdlc pack: workflows, shared files and skills, imported as text; beside the pack, `SDLC_LAB`: the lab's beat script with its captions, the stand-in's beats and the toy app (`assets/lab/`), which only `norn lab` reads
packages/conformance      @norn/conformance      contract suites (store, tracker, forge, signal source, harness), in-memory fakes, recorded-session replay
packages/cli              @norn/cli              wiring + commands, the layered config, plugin install and lock, init and doctor, `norn lab` (`src/lab/`); bin `norn` → src/main.ts
```

Dependencies point one way only: `schema ← plugin-api ← kernel ← runtime ← cli`. A plugin package reads only `schema` and `plugin-api` (`pack-sdlc` only `plugin-api`), so a third-party plugin needs nothing a bundled one does not; `conformance` adds `kernel`, since its harness suite replays through the kernel's reducer; `cli` wires them all. `test/repo/repo.test.ts` enforces this: every `@norn/*` import must be allowed **and** declared in the package's `package.json`. Bun's isolated linker also hides undeclared packages.

### The slots

A plugin is one value made with `defineNornPlugin({ name, api, provides })`; `api` is the plugin API range it was written against, and the cli refuses a plugin whose range this norn does not satisfy. Its name may not be `norn` or a slot's (`vcs`, `forge`, `tracker`, `store`, `harness`, `runner`, `pack`), since those lead a workflow's surface names (plugin API 1.21). `provides` fills any of these slots, each keyed by the name a config picks it by:

| Slot | Contract | Bundled |
|---|---|---|
| `harness` | the agent tool: install its hooks in a worktree, launch it, normalize its hook payloads into harness events, render norn's answer back | `claude`, `pi`, `lab` |
| `tracker` | where stories come from: list items, intake label, comments, close | `github`, `local` |
| `forge` | changes for review: open or update a change, read its state and checks, and (`checkReport`, optional, plugin API 1.27) each failed check with its link and whether the change conflicts with its base, which `forge.await-checks` reads, and (`fileUrl`, optional, plugin API 1.28) where it serves a commit's file, as an image or a link, for a forge that reports `raw_urls` | `github`, `none` |
| `store` | run data: numbered receipts, state by compare-and-swap, claims, mailbox, artifacts | `local`, `refs` |
| `vcs` | branches and worktrees: merge (never rebase), conflicts, push; and (`keepFiles`, `moveRef`, `pushRef`, optional, plugin API 1.28) a commit of given files on a ref only norn reads, the local ref moved to it fast-forward, and that ref pushed fast-forward | `git` |
| `runners` | where an agent process runs | `headless`, `herdr` |
| `stepKinds` | a step kind beyond the kernel's own, registered by its bare name and named in a workflow file by value, `by: <namespace>.<name>`: `slot` (plugin API 1.21) says which slot it works over (`vcs`, `forge`, `tracker`), and the namespace is that slot, else the plugin's name (`vercel.preview`); the loader resolves the surface name to the bare one, which a pinned document keeps as the step's head key. Its name and config keys stay apart from every step key (`STEP_KEYWORDS`: the thirteen keys of `STEP_KEYS`, which never grow, the older form's keys and the keys only a pinned document holds, `role` since 1.23), and its settings sit under `with:`; `reads` (plugin API 1.20) names what it reads that an agent step produces: a bare name must be produced on every path to it, `{name, fallback}` is optional and says what the kind does without it, and the host hands the kind each produced file's path as `input.reads`; a `wait` kind keeps nothing between polls, so the host hands it `input.started_at`, when its run started, to bound its wait (plugin API 1.27); the host hands it `input.evidence`, the evidence commit and files of the story's latest report with criteria, when that report kept any (plugin API 1.28); `produces` (plugin API 1.22) names the files it writes for later steps, each `{name, file}` relative to the story's spec folder under the path rule an agent step's follow (inside the folder, checked when the plugin is defined; never a file norn writes there nor a name norn provides as an input, checked when a workflow loads) and due on every outcome it answers: the host hands it each path as `input.produces` and reads the files back into the story's documents once it answers, so a later step reads them by name; `effects` (plugin API 1.24) names what a person must stand before (`KIND_EFFECTS`: `outward`, `cost`, `forge-write`), and the loader refuses a workflow file where some path to the kind passes no `by: person` step the policy leaves to the person (the floor, `kernel/src/workflow/floor.ts`) | `update-branch`, `integrate`, `push`, `verify-base` (vcs-git), `open-pr` (reads `pr_body`, with a fallback), `await-checks`, `await-merge` (runtime; `forge-write`) |
| `packs` | workflows, shared files and skills shipped together, and `roles` (plugin API 1.23): each role a step's `by:` names, with its `purpose` and the `CAPABILITIES` it may be granted (`role.ts`); a role that `supervises` does no step. The runtime hands the loader the pack's step roles, and a pack that registers none keeps the shipped ones (`AGENT_ROLES`) | `sdlc` |
| `signals` | a signal a waiting step can route under `on:`, named there `<namespace>.<name>` as a step kind is (`slot` since plugin API 1.21): its parameters, and `read` (a `Signal` with an occurrence id, `null` when nothing happened, or a failure when it cannot tell); optional since plugin API 1.19 | none: the host reports `vcs.stale`, `vcs.unpushed` and `norn.timeout` (the clock) itself, and a plugin may not reuse those names |

Every slot call returns a `PluginResult` and never throws. A plugin gets a `HostContext` (files, with `readBytes` and `writeBytes` for a file no text carries whole since plugin API 1.28, exec, processes, clock, the repo's root and data dir) and touches the machine only through it. A tracker, forge or store is never a state store for the kernel's decisions: labels and comments they write are display for people.

## Test tiers and CI

Tests come in two tiers, by folder:

- **unit**: `packages/<pkg>/test/unit/`, `test/repo/` and the rest of the root `test/` but `test/support/`. In-process only: a preload fails a unit test that starts a child process.
- **integration**: `packages/<pkg>/test/integration/`. Real git, real processes, the binary from source.

Shared helpers sit in `test/support/` and in each package's test folder. Tests never sit in `src/`. `test/repo/repo.test.ts` enforces the layout.

The unit tier (`bun run test`) and the type check must pass before you hand work back. **Commit only when `bun run test` and `bun run typecheck` are green**, and run both before every commit, not only before handing back. There is no `bun run lint`: the lints run inside the unit tier, so a red `bun run test` is a red lint too. They are:

- dependency direction, layout, glossary, path spelling and the IO ratchets in `test/repo/repo.test.ts`: file writes only in `@norn/host-node`, `JSON.parse` only in schema (and the few allowlisted tool-output reads), `Bun.spawn` only in host-node, and a pure kernel;
- the docs lint in `test/repo/docs.test.ts` (doc set in `test/support/docs.ts`);
- the repo's skills in `test/repo/process.test.ts`.

The docs lint fails on a rules file coming back, a link or anchor that does not resolve, a `norn` command or flag the CLI does not have, a version named outside the README badge and the changelog, and a handoff tracked in the repo outside a spec folder's `handoffs/`. A test also fails if the emitted JSON schemas or the generated blocks of `docs/reference.md` (`packages/cli/test/unit/reference.test.ts`) and `docs/workflows.md` (`packages/cli/test/unit/workflows-page.test.ts`) are stale.

CI (`.github/workflows/ci.yml`) runs the unit tier and the type check on every PR. Once they pass, it runs the integration tier in four shards, except the lab suites (the `lab*.test.ts` files in `packages/cli/test/integration/`), which each run alone on a runner, as the check `integration (<suite>)`: each plays a whole lab of real processes, and a lab next to other suites on one runner pushes every suite there past its timeout. It also builds the npm package and a binary and checks both with `scripts/smoke.sh`. The release run tests only the unit tier and the type check, since the release PR's CI ran every tier.

## Writing a test

Read `test/support/` first, then the support of the layer you test:

- `packages/conformance/src/fakes.ts`: `memoryHost`, `memoryFiles`, `scriptedExec`, `manualClock` and `steppingClock`, an in-memory `HostContext` any plugin or the runtime runs on.
- `packages/runtime/test/unit/support.ts`: a tick host over the real local store on memory files and recording fakes for tracker, forge, vcs, harness and launcher, so a test reads as the moments of a story.
- `packages/cli/test/unit/support.ts`: the cli in-process on an in-memory machine; `packages/cli/test/integration/world.ts`: a temp repo cloned from a bare remote, a temp norn home, and every call a subprocess of the binary from source, with the test harness plugin in `packages/cli/test/integration/fixtures/` installed through `norn plugin add`.

Take ref names and shapes from the code, never by hand: story keys and unit ids from `@norn/plugin-api` (`parseStoryKey`, `parseUnitId`), store refs from `packages/store-refs/src/layout.ts`, and receipt, run-state and config shapes from the kernel's model and `@norn/schema` (validate with `assertValid`).

## Golden cases

`packages/kernel/test/unit/golden.test.ts` replays every case in `packages/kernel/test/golden/` through `decide` and wants exactly the decisions recorded. The corpus fires every rule id in `RULE_IDS` at least once; `packages/kernel/test/unit/parity.test.ts` holds `packages/kernel/test/parity.md`, the map from the old engine's rules to the kernel's, to that list. A new rule id also needs its plain-word caption in `RULE_CAPTIONS` (`packages/cli/src/captions.ts`), which `norn tick` prints beside it; `packages/cli/test/unit/captions.test.ts` holds that map to `RULE_IDS` both ways.

A change that keeps behaviour leaves the corpus alone. For an intended change in what decide decides, run `bun run golden -- --update`. It decides each existing case again and rewrites only its `decisions` (names, facts, workflows and config stay), printing the decisions that went and came per case, so the diff is exactly the behaviour change; review it.

`bun run golden` alone only adds cases: it plays every scenario in `packages/kernel/scripts/golden/` through the model host and writes each case whose name is not in the corpus yet, never touching an existing one.

## Conformance suites

A slot's contract is a suite in `@norn/conformance` that every implementation runs, so a third-party plugin is held to the same reads as a bundled one:

- `storeContract`, `trackerContract` and `forgeContract` state what a store, tracker or forge must do (idempotent effects by receipt id, compare-and-swap that never lets two racing writers both win, refusals as `PluginResult` failures). Each bundled plugin runs its suite: `packages/store-local/test/unit/contract.test.ts`, `packages/store-refs/test/integration/contract.test.ts`, `packages/tracker-local/test/unit/contract.test.ts`, `packages/plugin-github/test/unit/contract.test.ts`, `packages/forge-none/test/unit/contract.test.ts`. Reference implementations in memory sit in `packages/conformance/test/unit/reference/`.
- `hostFilesContract` states what a host's files must do: text and, for a host that offers `readBytes` and `writeBytes` (together or neither), every byte value read back as written, a write replacing a file whole with no other name left beside it, and a missing file reading as null. host-node runs it in `packages/host-node/test/unit/files.test.ts`; `memoryFiles`, a copy of it without the byte methods and two copies broken on purpose run it in `packages/conformance/test/unit/contracts.test.ts`.
- `signalSourceContract` states what a signal source must do: nothing happened reads `null`, a signal is valid and of the name asked for, the same occurrence gives the same id on every read and on a fresh world (another machine), a new occurrence a new id, a source that cannot tell answers a failure, and a read performs no effect. The host's own vcs and clock sources run it in `packages/runtime/test/unit/signals.test.ts`; the reference in memory and three broken on purpose are in `packages/conformance/test/unit/reference/memory-signal.ts`.
- `harnessConformance` replays a recording of each scenario in one catalogue through the harness's `normalize` into the kernel's reducer and classifier, and asserts the read each capability implies. It reads `capabilities`, never `name`. The recordings are in `packages/conformance/test/unit/fixtures/`, run by `packages/conformance/test/unit/claude.test.ts` and `packages/conformance/test/unit/pi.test.ts`.
- The live canary, `packages/conformance/test/integration/live-canary.test.ts`, runs one real headless turn per harness and replays its hook calls the same way. It starts a real agent and costs money, so it runs only with `NORN_TEST_LIVE=1`, never in CI.

A new plugin gets a contract run; a known break is listed in the suite's options with its reason, and fixing it means removing the entry.

## Where the contracts live

- **The plugin contract**: `packages/plugin-api/src/`. `plugin.ts` (`defineNornPlugin`, `PluginProvides`, the checks a plugin passes when it loads), one file per slot (`harness.ts`, `tracker.ts`, `forge.ts`, `store.ts`, `vcs.ts`, `runner.ts`, `step-kind.ts`, `pack.ts`, `signal.ts` with `BUILTIN_SIGNALS`), `host.ts` (`HostContext`), `result.ts` (`PluginResult`, `ok`, `fail`), `events.ts` (the normalized harness events the kernel reads), `role.ts` (`RoleDefinition`, `CAPABILITIES`, `stepRoles`), `story-key.ts`, `version.ts` (`PLUGIN_API_VERSION`, `apiSatisfies`). A slot joins as an optional member, so a plugin written against an older plugin API stays valid.
- **The kernel's model**: `packages/kernel/src/model/`. `facts.ts` (`KernelFacts`, what a tick gathers), `actions.ts` (`Decision` and every action kind), `receipts.ts` (every receipt kind), `run-state.ts`, `session.ts`, `config.ts` (`KernelConfig`, the counter defaults, `bind`, the roles' capabilities and the policy's cap), `grant.ts` (a step's effective grant and its code level), `detect.ts` (`judgeChanges`, the rule a run that may not keep code is held to once it reports, and `LOCKFILES`), `capabilities.ts` (what the configured slots can do, as decide sees it, and `launchTarget`, the name an executor runs under in the runner an attendance picks).
- **decide**: `packages/kernel/src/decide/`. `index.ts` (entry), `story.ts` (intake, claims, the story's tail: flush, finish, release), `unit.ts` with `unit-agent.ts` and `unit-steps.ts`, `rules.ts` (`RULE_IDS`).
- **The journal**: `packages/kernel/src/journal/`. `journal.ts` holds the write rules (receipts before effects, state last by compare-and-swap, a lost race read again, anything failing validation read as corrupt); `apply.ts` turns receipts into run state; `format.ts` reads older run-state formats forward.
- **Workflows**: `packages/kernel/src/workflow/`. `load.ts` (the loader and its refusals), `counters.ts` (derived counters), `flatten.ts` (`use` and `like`), `actors.ts` (a step written with `by:`, `do:` and `with:` lowered to its head key, surface names to bare ones, and `signals:` and `entries:` to `base:`), `outcomes.ts` (outcome objects and `produces:` lists lowered to the pinned document's keys), `steps.ts` (head keys and step kinds), `produces.ts` (what agent steps produce, which outcomes each file is due on, and the flow check: a produced name an input or a step kind's `reads` names needs a producer on every path from `start`), `floor.ts` (a person's step before every effect a step kind declares), `guard.ts` (what of a workflow the person confirms). The runtime holds a changed repo workflow for the person in `packages/runtime/src/confirm.ts`.
- **Persisted formats and ids**: `packages/schema/src/*.ts`, `packages/schema/src/ids.ts` (`ulid`, `deriveUlid`, keys, slugs, `parseDuration`). Validate with `validate(name, value)` / `assertValid(name, value)`; never hand-roll checks of these shapes.
- **The config**: `packages/cli/src/config/schema.ts` (`NornConfig`, `ConfigLayer`, `CONFIG_DEFAULTS`), `packages/cli/src/config/paths.ts` (the layers and their files, the plugin lock), `packages/cli/src/config/derive.ts` (the kernel's and runtime's config from the person's, an executor without a runner of its own expanded to one launch target per attendance `runners:` sets). The norn home (`NORN_HOME_DIR`, else `~/.norn`) and the machine dir `~/.norn/repos/<id>/`, keyed by git's common dir: `packages/cli/src/home.ts`.
- **What an agent finds in its worktree**: `packages/runtime/src/inputs.ts` (the spec, the handoff, the produced files and the other inputs under `.agents/`; `HOST_INPUTS` is every input name the host provides, which the loader is given so it refuses any other name no step produces: a new input is its name there and its case in the switch beside it), `packages/runtime/src/skills.ts` (pack skills in `.agents/skills/`, linked from the harness's folder), `packages/runtime/src/story-docs.ts` (the spec and handoffs kept as store artifacts).

Change a contract only together with its tests, its conformance suite and every user of it.

## Code rules

[`AGENTS.md`](../AGENTS.md#rules) has them in short; here they are in full.

- **Glossary** (definitions in [Concepts](concepts.md#glossary)). Use the core nouns: story, slice, unit, workflow, step, run, claim, receipt, outcome, counter, gate, check, handoff, brief, tick, mode, worktree, plugin, slot, pack, harness, runner, executor, trace, mailbox. Banned synonyms: `task`/`job`/`ticket` → story/slice; state (for a workflow node) → step; lease (for ownership) → claim; result/status (for how a step ended) → outcome; `interactive step` → attended step. Outcomes are spelled as typed (`approve`, never `approved`). `test/repo/repo.test.ts` lints the unambiguous ones in package sources, `packages/pack-sdlc/assets`, `packages/schema/json` and every doc (the README, `CONTRIBUTING.md`, `docs/`, `AGENTS.md`). It matches whole words only and skips URLs, and in docs (not `.ts`) it skips inline code spans, so quote a banned word in backticks only when naming it on purpose.
- **Machine contract is JSON + exit codes.** Every CLI command prints one JSON value on stdout with `--json`, markdown without it. Failures and refusals print a `CliError` `{error, do_instead, code?}` and exit with an `ExitCode` (`refused` = 3 when a rule says no). No prose in JSON output; human hints go in `do_instead`. Never parse prose (handoffs, spec bodies) in decide.
- **Receipts before effects, state last.** Receipts are immutable and numbered; the journal writes the receipt of an effect before the effect, and commits the unit's state last, by compare-and-swap, as the commit point. A commit that lost a race is read again, never forced. Every record is validated on read; one that fails makes the unit `corrupt`, never a guess or a fresh start.
- **One IO boundary.** `@norn/host-node` builds the `HostContext`, and only it writes files (temp file → fsync → rename) or starts processes. The two harness plugins write the agent tool's own config file the same way, temp → fsync → rename; that is the one allowlisted exception.
- **The kernel is pure.** No `node:fs`, `Bun.spawn`, `Date.now()` or `Math.random` in `@norn/kernel`; use `facts.now` and `deriveUlid(tick_id, i)`, so a golden case replays exactly. The journal is the kernel's only IO, and only through the `Store`.
- **Plugins never decide.** A plugin reports facts and performs one effect per call, idempotent by its receipt id. A step kind performs and reports an outcome; the host records it as a receipt and decide picks the next step.
- **Comments say why, never what or when.** Write one only for what the code cannot say: an invariant, an ordering that must hold, a hazard, why the obvious way is wrong. No issue numbers, spec item ids or history in comments; that lives in the PR and the spec folder.
- **Code style.** TypeScript strict ESM, `.ts` import suffixes inside a package, `@norn/<pkg>` across packages, no default exports, small modules. Tests sit in their tier's folder (see [Test tiers and CI](#test-tiers-and-ci)).
- **No run state in the repo.** Do not commit trace data or run state: both live outside the repo, in the checkout's machine dir `~/.norn/repos/<id>/` (or on the store's refs).

## Process

norn develops norn. The person's side of the loop is in [`CONTRIBUTING.md`](../CONTRIBUTING.md#the-loop); the rules an agent must follow are in [`AGENTS.md`](../AGENTS.md#process). The detail behind them:

- **Where an agent changes the repo.** Only inside a norn step: after `norn brief`, in that unit's worktree. An ad-hoc session reads, explores, discusses and drafts issues; it never commits or creates a branch. To hand work over, the person runs `/issue`. Exceptions, each only when the person asks: the bypass and the one-time bootstrap.
- **The CI process check** (`scripts/process-check.ts`) passes a PR only from a story branch `norn/gh-N` (or `gh-N-<slug>`, the one older releases open) that closes #N, a valid bypass, or Dependabot, and refuses one that edits the skill copies `.agents/skills/norn*` unless it is a release PR (titled `Release X.Y.Z`).
- **What a step may change.** Inside a step, `.agents/workflows/` and the norn config files are ordinary repo files a story may change. A running unit keeps its pinned workflow; norn validates workflows when it loads them, and `norn doctor` shows the problems. Only norn's run state (in the machine dir or the store's refs, never in the worktree) is off limits. The spec and the unit's handoff are the files under `.agents/specs/<story>/` in the worktree: the agent edits them there and norn reads them back when it reports.
- **Released binary vs code under change.** The process (`norn brief`, `norn done`, hooks, `watch`) always runs the latest released `norn`, never a build of this repo. To exercise your change, run `bun packages/cli/src/main.ts …`, never `norn …`, and only in a throwaway git repo under `$TMPDIR` with its own `NORN_HOME_DIR`. A unit worktree is a live norn unit, and a dev build run there would act on its claim and run state. A broken release: the person reinstalls the previous release binary; the fix goes through the bypass if norn cannot deliver it.
- **Workflows.** A story runs the workflow its issue label `norn:wf:<name>` names, else the config's default. The shipped ones are in `packages/pack-sdlc/assets/workflows/`; this repo's test command is `checks.test` in `.agents/norn.yaml`, and its own files in `.agents/workflows/` (`release` and its triage, and `shared/diagnose.yaml`, the reproduce step its reproduce and fix rounds share) replace the pack's file of the same name.
- **Changelog.** Do not edit `CHANGELOG.md` in a PR. The `release` step writes it from the squash commits (see [Decisions](#decisions)).
- **The bypass, from an agent's side.** Only when the person asks, and only when norn cannot deliver the change. The person opens an issue labelled `bypass` that links the norn issue for the norn problem behind it. Work on branch `bypass/<issue>-<slug>`; the PR is labelled `bypass` and says `Closes #<bypass issue>`.
- **Friction.** When norn gets in the way while working here, say so in the handoff; the person files it with `/issue` and the `friction` label.

## Skills

- **Bundled skills.** The pack's skills are in `packages/pack-sdlc/assets/skills/`: edit them there. `.agents/skills/norn*` are this repo's committed copies, refreshed by the release step; never edit a copy.
- **Repo-local skills.** Skills without the `norn-` prefix (`release`, `release-start`, `issue`) are repo-local: edit them in place in `.agents/skills/<name>/SKILL.md` (linked from `.claude/skills/<name>`). `issue` and `release-start` are person-only (`disable-model-invocation: true`); an agent never runs them.
- **Exact or principled.** A bundled skill is exact in two places only: where code reads what the agent produces (report outcomes, the criteria and findings JSON, a file's fixed layout), because a reworded field breaks the reader; and where it is tuned to the agent tool (such as `norn-fsd-round`'s timeouts), because the number comes from how the tool behaves, not from judgement. Everywhere else a skill states the failure it prevents and the outcome to reach, and gives principles with their reasons, so the model can fit the work to the change in front of it; it keeps numbered steps only where order matters (check earlier findings before the diff, verify a finding before deciding). A fixed prompt to paste into a subagent or a word cap is procedure in place of judgement: say what the subagent must cover and why instead.
- **The `norn` skill** stays short and holds no workflow logic or step names: the brief carries the process, step skills carry the craft.

## Releases

A person runs `/release-start`. It opens the release issue. The `release` workflow rebuilds `CHANGELOG.md` from the squash commits since the last tag, bumps `version` in `packages/cli/package.json` and the README release badge, refreshes `.agents/skills/norn*` from `packages/pack-sdlc/assets/skills/`, opens the PR and waits for its CI. The person judges the version and the changelog at `ready`. Merging that PR smokes every binary on its own OS, tags `vX.Y.Z` and publishes in one CI run. See [Process](#process), and the decisions on publishing and the changelog below.

## Decisions

Deliberate choices that diverge from the obvious design.

- **A thin kernel, everything else a plugin.** The kernel holds only what must be the same for every repo: the workflow model, decide, the journal's write rules and the session reducer. Where stories come from, where changes are reviewed, where run data lives, which agent tool runs and where it runs are slots, so a repo with no code host (tracker `local`, forge `none`) and a team on GitHub run the same kernel. The bundled plugins ship in the binary; `norn plugin add` installs others into `~/.norn/plugins/` and pins them in a lock.
- **One package per plugin.** Each bundled plugin is its own package that reads only `schema` and `plugin-api`, so the dependency lint proves a bundled plugin uses nothing a third-party one could not.
- **The committed config wins.** The layers merge as built-in defaults, then `~/.norn/config.yaml`, then `.agents/norn.local.yaml`, then `.agents/norn.yaml`, the last one winning. A team that commits its config (`norn init --commit`) gets the same tracker, forge, store and workflows on every machine; a key it leaves unset is still each person's. The policy (`policy:`) is the one exception, merged the other way round (`narrowPolicy` in `config/load.ts`): only the user's file grants it and each repo file that sets a list keeps only what it names of the user's, since an agent inside its step can change a repo file but not the person's own.
- **The person's floor is checked when a workflow loads; what they stand on is confirmed.** A step kind declares the effects a person must stand before (`effects`, plugin API 1.24), and the loader refuses a workflow file where some path from `start` or the update-branch entry reaches one without a gate no policy grant delegates (`kernel/src/workflow/floor.ts`); a pinned revision loads without it, so a grant made since never takes a round's workflow away. A refusal the person's grant alone causes carries `granted` (the file stands on the floor with nothing delegated), and the cli treats it as the policy to narrow, never as a broken pack: `packFailure` skips that workflow, as it skips a held one, so ticks and pinned units go on, and doctor and `workflowRefusal` name `policy.stand_in.gates`. A repo file whose change touches a gate, `attended:` or `allow:` (`kernel/src/workflow/guard.ts`) is held in the runtime (`runtime/src/confirm.ts`): new rounds run the revision the person last confirmed, kept in the machine dir by `norn workflow confirm`, else the pack's. The pack's own files are trusted as the binary the person installed, so only the repo's layer is weighed, and a change matching either trusted revision's guarded parts runs as it is. A held workflow stops no tick: doctor names it, and a story asking for one with nothing to run parks.
- **One spelling pins.** An outcome written as an object (`means`, `verdict`, `produces` on the outcome) and a step's `produces:` list are a file's form only. The loader lowers them in `outcomes.ts`, after a `like` copy is filled and before anything reads the step, to the keys a pinned document has always held (`means:`, `verdict:`, `criteria: required`, `hand_back:`, `produces: {<name>: {file, on}}`). A unit's pin, its hash and the golden cases so never depend on how a file spells a workflow, and every revision pinned before keeps loading. A test pins each new spelling against the older one it lowers to (`packages/kernel/test/unit/workflow-outcomes.test.ts`).
- **The pinned document grows only by optional keys.** A workflow's `sources:` and a read marked optional (`notes?`, `brand?`) are the first things the pinned `WorkflowDocument` holds beyond the older form. Each is optional and written only when a file uses it, so a workflow without them pins the hash it always did, every revision pinned before keeps loading, and only a workflow that uses them pins a new hash. A spelling that means the same as an older one still lowers to it: `findings?` pins as `last_findings`, and `?` on one of norn's own inputs is dropped (`packages/kernel/test/unit/workflow-sources.test.ts`).
- **A closed step language, named by value.** A file writes a step with `by:`, `do:` and `with:` among thirteen keys (`STEP_KEYS`) that never grow; a step kind or signal is named by its namespace (`forge.open-pr`, `vcs.stale`), never as a key, so a plugin cannot collide with a keyword and a workflow moves between providers. `actors.ts` lowers it, like the outcome objects, to the pinned document's head key and bare registry names, so registry patterns, derived counter names (`<step>.<outcome>`) and `reset_on` keep one dot and a pin's hash never depends on which form a file used. Plugin config keys still sit beside the head in a pinned step, which is why `STEP_KEYWORDS` keeps the older form's keys reserved for good.
- **Steps declare what they hand each other.** A file one step writes for another is declared (`produces:` on the agent step, `reads` on a step kind), never promised only in prose: the loader checks the flow over the flattened graph, a producer before every reader on every path, and `norn done` refuses a report without a file its outcome is due on. The flow check needs the host's input names, so, like the input-name check, it runs on pack and repo files and not on a pinned revision, which was checked when it was pinned and must keep loading if a step kind later declares a read. A read with a fallback exists for a path the graph cannot see through: the light path of a base update reaches `open-pr` without `describe`, but only on a change an earlier pass described, whose `pr.md` the worktree still holds.
- **The spec and handoffs live with the run data, not on the branch.** A story's documents are store artifacts. Before a launch, and whenever `norn brief` renders, norn writes them into the worktree under `.agents/specs/<story>/` (every other input under the run folder's `.agents/run/in/`, beside the `out/` a run writes its reports to), each folder with a `.gitignore` of `*`, and reads back what the agent changed when it reports. A PR then holds only code, and nothing the agent reads is ever committed by accident.
- **Pack skills are written before every launch.** Each pack skill goes to `.agents/skills/<name>/` in the worktree, ignored by git, and the harness's own folder (`.claude/skills/`, `.pi/skills/`) gets a link to it. A folder of that name the repo commits itself carries no norn mark and is left alone, so a repo overrides a pack skill by committing its own.
- **The main checkout gets the same skills from doctor.** A person runs `/norn-fsd`, `/norn-retro` and `/norn-triage` in their own session, which no launch reaches, so doctor's `skills` check (which init runs) writes the same marked copies and links into the main checkout and brings them up to date on each run, removing norn's copies, files and links of skills a newer pack dropped (the checkout outlives an upgrade, a unit worktree does not). This repo's committed `.agents/skills/norn*` copies carry no mark and stay as the release step left them.
- **Person-only commands are refused by the CLI, not by each harness.** A command a person alone runs carries `personOnly: true` on its definition (`packages/cli/src/command.ts`), and the dispatcher refuses it with `person_only` before reading its arguments when the launch env (`RUN_ENV`: `NORN_UNIT`, `NORN_RUN_ID`) is set (`packages/cli/src/person-only.ts`). The launch env reaches every process an agent starts, under any harness or runner, so one check covers them all; a harness guard would cover one tool. A shell clears its own env, so the check also reads the env each ancestor process was started with, which no descendant can rewrite, through `@norn/host-node`'s `nodeAncestry` (`/proc` on Linux, `ps -E` elsewhere) handed to the CLI as `HostFactory.ancestry`; an ancestry it cannot read refuses. There is no override flag, since an agent could pass it.
- **Hooks go in the agent tool's local settings only.** The claude harness writes `.claude/settings.local.json` in each worktree at launch, never the committed `settings.json`, so a machine-specific hook command never follows the branch into a clone where it does not exist. A marked `.claude/.gitignore` beside it names the file and itself, so the worktree stays clean for a branch update and an agent's `git add -A` never commits the hooks; a `.claude/.gitignore` without norn's mark is the repo's and is never rewritten.
- **The executor and runner a step runs on are decided, never refused.** A workflow names a role and who stays beside the agent (`attended:`); the machine binds the role, or the step, to executors (`bind:`) and each attendance to a runner (`runners:`). The CLI expands an executor without a runner of its own into one launch target per attendance (`deep@person`, `launchTarget`), so the launcher, the session source and every capability lookup key by one name as before, and a run's record names both. decide picks the first executor in the binding that matches the step as facts it reads (`ExecutorCapabilities`): configured, `attended` (presence) for `attended: person`, `denyTool` for a docs-only step, and parks `agent.no_executor`, `agent.no_presence` or `agent.unguarded` otherwise, before an attended step waits for its person. An attended step on a runner without presence used to run as an auto run once a person started it; it parks now, so a person is never promised a pane that never opens. The role is pinned (`role:` on the agent step), the binding is not, so a pin keeps its hash while each machine runs it where it can.
- **A step's grant is decided, and detection is receipted effects.** The pack registers each role's capabilities; decide narrows them by the pinned `allow:` and caps them by `policy.allow` (`grantOf`) on each tick, so the brief, the launcher and detection read one grant and a pin keeps its hash while a machine's policy changes. A run whose grant may not keep code starts under `code: read | scratch` on its `run.started`: the host writes the visit's snapshot as a `run.snapshot` receipt after the intent and before the launch (`runtime/src/detect.ts`, the vcs's `snapshot`, plugin API 1.25), or a failed one, which parks the unit. vcs-git builds the tracked tree in a throwaway index seeded from `ls-files --stage` plus the paths `diff-files` names, never `stash create` (it refreshes and writes the worktree's index) and never a copy of the index file (its newer mtime would trust racily clean entries), so a file whose stat alone changed moves nothing. A `done` from such a run is not applied until `agent.check` (`check_run`) has killed the run's processes, compared, and reset under `run.checking` and `run.checked`; a refused or failed check vetoes the report in `applyReceipts` and parks. `judgeChanges` is pure and shared by `norn done`'s early refusal and the tick's check, so both judge alike. Refs, config and hooks are digests the vcs computes; a ref other than the unit's that moved is only noted, as parallel slices move theirs. A run's hook config is pinned as a digest on its launch's `run.started` (`Harness.hookConfig`, plugin API 1.25). A plugin's kinds' effects are accepted at `norn plugin add` (`cli/src/plugins/accepted.ts`), and a kind over a slot takes the core's (`SLOT_KIND_EFFECTS`).
- **Worktree setup is a runtime gate, not a step.** `prepareWorktree` (`runtime/src/setup.ts`) stands in front of an agent launch and a check, never a step kind: it runs `setup.command` detached when the worktree is new or the digest of the command and its inputs differs from the one recorded after its last success, and the launch waits without writing its intent, so no retry or counter is spent. Its record is machine-local (`runtime/setup/`), read leniently (an invalid one is dropped and the setup runs again), never run data. A failure is a `unit.parked` receipt the host writes itself, as `norn run stop` does, under an id derived from the failed setup, so a rerun that lifts it makes the next record a replay and the setup runs again. decide is unchanged: `worktree.setup.failed` is no derived park, so the unit holds until a person acts; the kernel only gained `unit.parked`'s optional `text`. A design with its own receipts, action and fact would have bumped the plugin API and the golden cases for a step a person never routes.
- **A supervisor is a second run of the visit, held by identity.** decide launches it (`start_supervisor`, `kernel/src/decide/supervisor.ts`) beside the step's own run and keeps it on the state as `supervisor`, apart from `run`, with what stood in for the person this visit as `supervised` (answers counted against the pinned `asks`, subjects handed back); entering a step drops both. Its report goes through the same `norn done`, recognised by its run id (`runtime/src/supervisor.ts`), and becomes the receipt its subject takes: an `answer.sent` or a delegated `gate.decided` carrying `supervisor_run`, which `applyReceipts` refuses from any run but the visit's supervisor, or a `supervisor.escalated`. A question naming what only a person grants is read by the host into `question_reserved`, so decide never reads the question. No gate is delegated yet: `delegationBlocked` names the first executor outside a `sandbox` (plugin API 1.26), since without one an agent's shell could write the decision itself, and with every executor sandboxed still refuses, since the bound on the steps after a delegated gate and the author allowlist the design makes conditions of delegation are not built; the core builds no sandbox.
- **A docs-only step fails closed.** `writes: docs` is held by the hook guard alone (`packages/runtime/src/events/answer.ts`), so it is no stronger than the harness's `denyTool`. decide parks such a step `agent.unguarded` before it starts on an executor whose harness lacks it, as it parks `agent.no_executor`, and the launcher refuses the start too (`AgentRunRequest.writes`), for a run whose executor's harness changed under it. The guard reads the rule from the run's own step (its `run.started` receipt and the pinned workflow), so a run left behind by a moved step keeps its own rule; only when the record cannot be read (unreadable or corrupt) does it hold the launch env's `NORN_WRITES=docs` (`WRITES_ENV`, set to the step's `writes` on every launch and resume, so a value inherited from the launching process never stands), so it never falls back to the worktree rule. A run whose grant may only read code is guarded the same way whatever its pin says of writes: its `run.started` carries `code: read`, which the guard reads as `docs`. It judges file-tool writes only, as for every step: a shell write is not seen. `writes` is a step keyword (plugin API 1.20, with `produces`), so no step kind takes a config key of that name.
- **Claude sessions run in `auto` permission mode by default.** Permission profiles per step are not built ([Limitations](limitations.md)). A permission prompt parks the unit (`agent.permission.park`, its text naming the call from the pending `tool.requested`), and `story answer` records the answer `to: dialog`, which the tick turns into the harness's `dialogKeys` pressed through the runner's `keys` (plugin API 1.12), only while the run's events still show that prompt open. On the machine that launched the run, `story answer` first reads the pane and refuses an option its menu lacks (`not_an_option`, exit 3) with an answer the shown dialog does take, before anything is recorded: a recorded answer the menu cannot take could never be pressed, and could not be replaced. A run alive in a pane that sends no event for the silent window (its hooks never loaded, as behind a trust prompt) parks as `agent.no_events.park` rather than being retried into the same prompt in a fresh pane. A runner that can read its pane offers `dialog` (plugin API 1.15; herdr reads the screen while it reports the agent `blocked`): the tick reads it for a live run with no event yet (`run_dialog`), and decide parks on it at once with the dialog's text, so the silent window is only the fallback for a pane nobody can read. When it presses an answer's keys, the launcher hands the harness the dialog as the pane shows it, so a menu with no numbers (Claude Code's trust prompt, which lists `No, exit` first) is moved through from its cursor to the option that says yes. The claude harness's default args are `--permission-mode auto` (`DEFAULT_ARGS`); an executor's `args` replaces them whole, permission mode included.
- **Published as `@pruszynskijakub/norn` on GitHub Packages.** The workspace package stays `@norn/cli`; GitHub's npm registry only takes a package under its owner's scope, so the release build renames it (`bun scripts/build.ts --name … --registry …`). The packs and harnesses import their assets as text, so the bundle and the binary carry every workflow, skill and extension. Merging the release PR runs one CI workflow that creates tag `vX.Y.Z`, tests, publishes the package and attaches the binaries to a GitHub release. Tag and publish share one run because a tag pushed with `GITHUB_TOKEN` triggers no other workflow.
- **The store keeps a norn version floor, not the config.** Receipt and state shapes grow with norn, and an older norn reads a newer shape as invalid and marks the unit corrupt, so every norn acting on one store must be at least as new as the newest that wrote it. A store may offer `floor` (plugin API 1.13): `local` keeps it in `runs-v2/floor.json`, `refs` on `refs/norn/v2/floor`, pushed under a lease like a claim. A command marked `acts` checks the floor when it first builds its runtime env (`packages/cli/src/version-guard.ts`): below it, it refuses with `version_too_old` (exit 3) before it writes anything; above it, it raises the floor to its own release before it acts, so no write of a newer norn reaches an older one that was not refused first. A pre-release or dev build compares as the release it leads to; a build that names no version (only a test passes one) is never checked; a floor the store cannot read or raise is noted on stderr and lets the command act, so an offline `refs` clone still ticks. Read-only commands, `init`, `config`, `plugin` and `hook` are not checked, so a person can still see a story and fix a setup; `watch` checks before each tick and pauses with one `paused` line. The floor rises on any newer release, not only one that changed a shape: telling the two apart would need every shape change to carry its own version, and a missed one is a corrupt unit. The old `norn_version` config key is gone: it held a version a person had to bump by hand and commit.
- **The machine dir is keyed by git's common dir.** Every worktree of one clone, a unit's included, shares `~/.norn/repos/<id>/`, and two clones never do. The claim holder is not keyed by it: two clones on one machine under one user are one holder (`user@` the machine's LocalHostName, else its hostname) unless the config names a `holder` ([Limitations](limitations.md)). The derived holder is fixed on first use in `<home>/holder.json` with the names this home claimed under before (`former`), since macOS's hostname follows the network: every process reads it back, a claim under a former name is this machine's (a report goes through), and the tick moves it to the holder by a versioned takeover before decide reads it. A configured `holder` has no former names: it is set to tell this home from another that claims as the derived name. A Stop hook does not wait for the report of a run whose claim moved, since that report is refused (`claim_moved`).
- **A takeover starts from the work and the shared record.** A held story's flush publishes each unit's branch head first (the vcs's `publishHead`, plugin API 1.16: git pushes it to `refs/norn/heads/<branch>`, never a branch, fast-forward only under a lease on the last fetched copy) and its run data after, so the remote's record never names a step whose work it lacks; the tick's fetch brings the published heads back, and `worktree.ensure` cuts a new branch from the newer of the remote's branch and its published head. A report from a run whose story's claim another holder took is refused on the old machine (`claim_moved`, kept as a `hook.error` in the run's log), so its copy of the record never moves ahead. A shared store may offer `diverged` and `adoptRemote` (plugin API 1.16): a story whose run data here and on the remote diverged reads as `unsynced`, on a story this machine holds, decide holds it (`store.diverged`) and never flushes it, `status`, `story view` and `doctor` show it, and `norn story take --force` carries it on from the remote's record, keeping this clone's part under `refs/norn/v2/dropped/runs/`. On a story another machine holds, the tick's sync carries it on from the remote's record at once, as only the holder's writes are ever published. An existing worktree is moved forward (fast-forward only) to a newer carried head when its unit runs, and refused with `conflict` when it diverged from it.
- **norn develops norn (self-hosting).** Every change to a file in the repo starts as a norn issue and lands through a norn workflow; an agent changes the repo only inside a norn step (see [Process](#process)). Outside norn: Dependabot PRs, GitHub settings, backlog triage, the bypass, and the one-time bootstrap. Enforced by these docs and the CI process check, not by an editor hook.
- **Squash-only merges; the changelog is written at release.** Every merge to `main` is a squash whose message is the PR title and description, so each commit is one PR (`Closes #N`). PRs do not edit `CHANGELOG.md` and there is no `## [Unreleased]` section: the `release` step writes `## [X.Y.Z] - <date>` from the commits since the last tag.
