# auto-mode dogfood — friction and defects

- **A1 (defect, herdr runner): agents in herdr panes run the wrong `norn`.** The herdr runner launches the agent through the pane's login shell; the user's zsh rc puts `~/.local/bin` first, where an unrelated global `norn` 0.11.0 lives. Passing `PATH` via the agent's `env` (→ `herdr --env`) does not help: the rc re-prepends. An agent following the norn skill would run `norn brief` against the wrong tool. norn does not set an absolute `norn` path for the agent (A6 sets NORN_HOME/STORY/RUN only) and `doctor` does not check which `norn` an agent will see. Headless is fine (inherits watch's PATH). Workaround: agent `command:` = `claude-b.sh` that re-exports PATH. Evidence: herdr-path.txt, herdr-path2.txt.
- **A2 (observability): a story claimed by another checkout is invisible, and its intake repeats every sync.** In A, after B claimed gh-9, every sync tick emits `remote.intake` for gh-9 with `ok:true` and detail `skipped: …already exists on origin, do_instead: norn take gh-9`. It is a non-noop decision in `watch` output each sync forever; `norn status gh-9` says `unknown story gh-9`; `inbox` shows nothing (no "held by B" / "Unclaimed" line, cf. T10). The only hint is buried in the tick JSON. Evidence: a-setup-tick2/3.json.
- **A3 (minor): no way to validate a workflow file on its own (W5).** I validated `quick.yaml` indirectly via `norn workflow gh-4 quick --to implement` (reaches `unit_done` only if validation passed). `doctor` does not validate workflows.
- **A4 (defect, herdr): first launch in a new worktree hits Claude's folder-trust dialog, and norn's answer path cannot get past it.** Every story/slice worktree is a new folder, so every herdr launch shows "Is this a project you trust?". norn classifies it correctly as an implicit `ask` (good), but (a) the inbox "question" is the raw 15-line screen dump with box-drawing rules; (b) `norn answer` goes through `herdr agent prompt`, which herdr refuses for a blocked agent (`agent … is blocked and requires interactive input`); the result is recorded only as `delivered: "not delivered: …"` inside an ok:true decision, the unit goes back to `running`, and one tick later re-parks with the same ask — the person's answer is lost and nothing says so in `inbox`; (c) after typing into the pane by hand, Claude has dropped the launch prompt, so the agent idles until a second answer re-sends "Use the norn skill…". Headless (`-p`) skips the dialog. Evidence: b-pane-ask1.txt, snaps/03-implicit-ask, B trace tick 01M5PM38NRG6BFN62NWDZJAE9S.
- **A5 (observability): `trace --text` folds runs together.** After two kills and a retry, gh-10 shows one row `implement#1 … (in step)` whose WHO column is a list of tick ids, with "agent.died: process gone, no receipt" twice; no run ids, no "retry 1/1", no pids. `status`/`inbox` "Running gh-10 implement #1 (auto)" do not say it is a retry. The classify receipts themselves are complete (counter retries 1/1).
- **A6 (minor): `status` of a stuck unit still lists it under "Runs" (`implement#1 auto claude since …`)** although no process is alive.
- **A7 (observability): permission-prompt inbox items are unreadable.** The `ask` question is the raw visible screen (box-drawing rules, code lines), and the pending command is the whole heredoc; `inbox --text` prints ~70 lines for one item and the actual question ("Do you want to proceed? 1. Yes 2. … 3. No") is at the bottom. `status --text` puts the first screen line into the one-line summary (`parked implement#1 (ask: │       expect(press("q", …`). The suggested fix `norn answer gh-9 "…"` cannot answer a permission dialog (see A4); the person must type into the pane, then still `norn answer` to unpark (C3).
- **A8 (observability): an auto-mode step queued on max_agents looks like a manual step.** gh-11 (mode auto) waiting for a free agent slot shows `ready implement#1` plus the manual-mode hint `cd … && claude '…norn brief'` in `status`; nothing says "queued: max_agents 2 in use" (the decide noop has that text, only in the trace).
- **A9 (defect, headless): `stalled`/`timeout`/`silent` on a headless run decide `nudge`, which always fails.** `classifyRun` treats a session as typable when `session.runner === machine.runner`; for headless that is true but `send` throws `unsupported`. Result: decision `agent.stalled.nudge` ok:false (`failed: 1` in watch), the classify receipt is on disk but state.json is not written in that tick (applied one tick later), and no B2 resume (`--resume <agent_session_id>`) is attempted although the receipt path for answers does exactly that. The nudge counter is spent with nothing delivered; the second window goes to `$stuck`. Evidence: watch-A.log 09:41:58, snaps/08-stalled-headless.
- **A10 (observability): orphan run after a heartbeat crash.** After INJ 4b the run has a `started` receipt with no session; norn never learns the pane/pid (hook facts with that run_id do arrive: SessionStart at 09:38:18), so `died` cannot fire, `nudge` cannot be delivered, and the orphan claude pane stays open. The inbox calls it "agent ended its turn without reporting" (it did not; it never got a prompt). `status` lists it under Runs as `review#1 auto claude since …`. Recovery needed a person to find the pane by hand.
- **A11 (herdr): the launch prompt is not submitted.** In both herdr launches (gh-9 implement, gh-9 review) Claude came up interactive with an empty input box ("Try \"fix lint errors\""); SessionStart fired but no UserPromptSubmit. For implement the trust dialog may explain it; for review there was no dialog (folder already trusted) — the positional prompt still did not run. Unclear whether this is Claude 2.1.310 or the herdr `pane run` path; either way norn reports the run as `running` until `stalled` 3 min later. Evidence: b-pane-orphan.txt, B trace hooks 09:38:18.
- **A12 (herdr): finished panes are never closed.** The `gh-9 implement` workspace (wP) still holds an idle claude after `implement.done`; each step adds a workspace. Nothing in status/inbox lists them; `tidy` does not mention them.
- **A13: config is read once per `watch` process.** Editing `.agents/norn/config.yaml` (agent args) had no effect on later launches until the watch restarted; nothing says so.
- **A14 (defect): an implicit `ask` for a permission prompt blocks the approved command itself.** The person approves the prompt in the pane; the command was `norn done …`; norn refuses it with `parked_ask` because the unit is parked on that same implicit ask until `norn answer`. The agent then stops. Order matters and nothing tells the person to `norn answer` *before* pressing Enter. Combined with A10 (no session) the answer started a fresh agent, discarding a finished review (duplicate effect: two review runs for one step). Evidence: b-pane-orphan-end.txt, B receipts 0016–0019.
- **A15 (defect): claim renewal starves remote lifecycle.** One action per unit per tick (F13): on every tick that has fresh remote facts the story also renews its claim (sync_interval 1m = renew 1m here), so `remote.pr_merged` never ran for gh-10 for 15 min until I ran `norn sync` by hand. With defaults (renew 3m, sync 5m) it would hit every 15 min. Evidence: A trace sync ticks 09:48:13–09:52:13 (`claim.renew` only, pr state `merged` in facts).
- **A16 (defect, herdr): `silent` cannot fire from pane state.** The herdr adapter returns `since: null`; decide counts an idle/done pane as a turn end only when `since > touched`. After an interrupted turn (no Stop hook, no idle_prompt) the agent was classified `stalled` after the full 3m window instead of `silent` at the next tick. The nudge itself worked (same session).
- **A17 (observability): takeover is invisible in the record.** A non-forced `take` writes no receipt and no trace row in the unit timeline (`trace gh-9` shows implement#3 continuing with a `died` classify); `holder` is `user@machine`, identical for two checkouts on one machine, so even the claim blob does not tell who held it — only heartbeat_id differs. The returning checkout B shows the story as `mine · running` (A18).
- **A18 (defect, observability): returning checkout believes it still owns the story.** After A's takeover, B's `status` prints `mine` and `running implement#3`, `inbox` lists it under Running; B's decide correctly says `claim.other`. B's worktree holds an unpushed `0035-done` receipt whose number A has reused for a different receipt (`0035-classify`) — a guaranteed conflict if B ever pushes; nothing warns. Evidence: B status after 12:06:56, B and A receipts dirs.
- **A20 (observability): a merged story stays alive on a non-holder checkout.** B never applies GR6 for gh-9 (it is not the holder; claim ref deleted → `claim.unclaimed`). B's inbox offers "Unclaimed — `norn take gh-9`" for a merged story, status says `running implement#3`, and `tidy` reports no orphans. Same for A's leftover gh-15 worktree after losing the intake race.
- **A21 (defect): the loser of an intake race grabs the story later — even after it is merged.** A intook gh-15 locally and lost the claim CAS to B (correct). When B finished, merged and deleted the claim ref (GR6), A's local copy was still `new` with no state, so `decideStory` treated it as `fresh` and acquired the claim of a merged story; A's clean exit then failed to release it (push of A's stale branch rejected), leaving a claim ref on origin until a manual `norn sync` in A. Evidence: watch-A.log 10:17:43 and the final summary line.
